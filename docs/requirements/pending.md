## 3. 待评估方向

### 3.1 足迹行程清单（重「计划」）

**状态：🔵 待拍板。** 0.0.3 只做「计划 = 时间」（轻），足迹的「计划 = 内容」（重）形状不同且需新增表，作为独立版本候选。决策项为 §2.5 的 D-24 ~ D-27。

#### 条目粒度：一个条目 = 一个目的地（而非一次旅行）

这是本节的前提，也是最容易搞错的一点。跨城旅行（如「云南行」含大理 / 丽江 / 香格里拉）**不是「一个条目装不下」的问题，而是它本来就该是多个条目**：

| 场景 | 条目 | 清单 |
| --- | --- | --- |
| 广州周末 | 「广州」1 条 | 清单：珠江夜游 / 早茶 |
| 云南 7 天 | 「大理」「丽江」「香格里拉」3 条 | 各自清单：洱海·古城·米线 / 玉龙雪山·古城 / 松赞林寺 |

一次旅行是**多条条目之间的关系**，不是单个条目的属性。这与现有数据模型一致：`sgj_item_place` 的 `city` / `province` / `latitude` / `longitude` 均为单值字段，且地图为**图钉制**——`/app/travel/trajectory` 返回 `visited` / `wish` 两组点，`TravelMap` 以 `AMap.Marker` 逐点渲染，**无 polyline，所谓「轨迹」并非连线**。若强行让一个条目代表一次跨城旅行，该条目的坐标只能取其一，地图会退化为一个图钉并丢失其余城市。

「整趟旅行」若要成为一个整体概念（有标题、起止、顺序、总进度），需引入行程容器——当前**不做**，见 [0.0.3-plan.md](0.0.3-plan.md) 的非目标与 D-27。

#### 形状

| 项 | 说明 |
| --- | --- |
| 表 | `sgj_item_todo`（暂名），字段建议 `item_id` / `title` / `done_flag` / `done_date` / `sort_order` |
| 形态 | **可选**。有清单时展示进度条（已完成 / 总数）；无清单时行为完全不变 |
| 完成语义 | **清单不 gate 条目的 `DONE`。**「去过大理」在你到达那一刻即为事实，与清单勾选无关——清单留着「没吃到米线」，不代表没去过大理。清单只提供**进度感与满足感**（如标题旁显示 `大理 · 3/5 已打卡`），条目状态仍由手动流转决定 |
| 暴露范围 | 前台先在足迹详情暴露。可参照既有先例：`sgj_item_photo` 挂在 `sgj_item` 上（任何类型皆可存），但前台仅足迹页使用——`PhotoDeck` / `PhotoAlbumDialog` 仅在 `views/front/travel/index.vue` 引用 |
| 扩展性 | 若后续书籍需「读这几章」、剧集需「补这几集」，同一能力可直接开放，无需再建表 |

**需避免的做法**：用笔记正文的 `- [ ]` 清单充当待办。`MarkdownViewer` 已开启 `gfm` 且为 `input[type="checkbox"]` 写了样式，`marked` 亦支持 task list，**渲染结果形似待办清单，但 checkbox 为 `disabled` 实际不可点击**——属「看着能用」的误导。若要做到可交互，需在笔记正文中做结构化数据回写，违反「`content` 保持纯 Markdown」的约束，并影响后续 AI 切块。

### 3.2 多人化（多用户社区站）

**状态：⚪ 待评估。** 是否实施未定，此处仅记录前置条件、障碍与决策点，不做设计。决策项为 §2.4 的 D-17 ~ D-23。

#### 概念边界

本节的「多人化」指**多用户社区站**（一个站点，多个用户各自记录，主页可公开浏览他人的空间），**不是多租户**（一套部署服务多个互相隔离的组织，各自有管理员与配置边界）。前者与现有 `create_by` 模型天然兼容，不涉及多租户改造，因此不与「明确不做：多租户」冲突。

#### 现成基础（无需改造）

- **数据隔离已实现**：`AppScopeHelper.resolveCreateBy()` 已按 `create_by` 区分「匿名访客 / 博主本人 / 管理员 / 其他登录用户」四类可见范围，用户数据接口（`/app/item`、`/app/note`、`/app/home`、`/app/travel`）均经其过滤。这是多人化最难的结构，已在代码中。**例外**：`/app/tag` 不过滤，因标签是模块级共享词表而非用户数据（见下方 A 末条）；
- **注册流程完整**：`SysRegisterController` + `SysRegisterService` + 前台 `register.vue` + 登录页入口齐备，仅由配置 `sys.account.registerUser`（默认 `false`）关闭；
- **注册用户无角色**：`SysUserServiceImpl.registerUser` 仅执行 `insertUser`，不分配角色，故注册用户可在前台记录、后台为空。此形状与「前台面向用户、后台面向运维」的定位一致；
- **资料字段齐备**：`sys_user` 已有 `nick_name` / `avatar` / `email` / `sex` / `remark`，头像上传页面亦已存在；
- **所有业务表带 `create_by`**，天然按用户归属；文件服务已兼容 S3 协议，具备多用户存储基础。

#### 主要障碍

**A. 公开性模型（工程问题，必须先解决）**

- 现为单值配置 `shiguangji.public-owner`，匿名访客只能访问单一账号的数据。多人化需支持按用户定位空间（路由形态见 D-19）；
- **`sgj_item` 无 `is_public` 字段**（仅 `sgj_note` 有，见 `init_business.sql`）。条目无法逐条控制公开性，多人模式下只能全公开或全不公开，而公开展示类需求依赖此字段；
- `maskItemForGuest` / `maskNoteForGuest` 的脱敏规则按「单一博主」设计，多人化后需重新定义访客观看他人空间时 `comment` / `rating` 的可见性；
- **标签的归属未定**：`sgj_tag` 表有 `create_by` 字段，但按标签管理的既定语义，标签属「模块级共享词表」而非用户数据（同一模块内唯一、不同模块可同名），`/app/tag/list` 亦为匿名共享接口、不做范围过滤。此设计在单人模式下成立；多人化后需明确标签是**全局共享词表**（由运维统一维护）还是**每用户私有词表**。若为前者，则普通用户无法纳管自己的标签；若为后者，则 `sgj_tag` 的唯一性约束需由「模块内唯一」改为「模块 + 用户内唯一」，属表结构变更。

**B. 隐私边界（需先拍板的承诺，非技术问题）**

- `resolveCreateBy()` 对 `publicOwner` 与管理员返回 `null`，即**不限制、可见全部用户数据**。单人模式下等价于「站长看自己的数据」，多人模式下则成为「站长可读所有用户私密内容」；
- `admin` 与 `publicOwner` 默认同值，多人化后应拆分为「运维身份」与「首页展示账号」两个概念。

**C. 内容审核与合规（最重，且不是工程问题）**

- 一旦平台主动展示用户内容，产品性质由「个人记录工具」转为「内容平台」，需承担举报、删除、封禁、审核队列等责任，并涉及内容合规要求；
- **匿名展示不等于脱敏**：时间、地点与标题的组合可反推作者身份。故展示必须由用户**主动选择参与**，不得默认入选——此举同时约束隐私风险与审核范围。

**D. 运维成本**

- 备份、限流、防刷注册、容量规划，以及用户支持本身。

#### 建议的推进方式（若决定实施）

**第一步：多用户，不含公开展示。** 目标为验证「多用户可用」，不引入审核负担。范围：开启注册、独立用户空间与路由、`sgj_item` 增加 `is_public`、拆分 `admin` 与 `publicOwner` 且管理员不再跨用户读取私密数据、个人资料页。

**第二步：公开展示。** 待第一步有真实用户且运行稳定后再评估。范围：用户主动参与机制、跨用户聚合 feed 接口、举报与删除机制。

**注意**：展示类交互（滚动内容墙等）位于链路最下游，依赖第一步的公开性字段与第二步的授权机制先成立，不宜作为起点。

#### 与现行版本的唯一交叉点

`sgj_item.is_public` 同时是：现有结构性缺口（仅笔记可逐条控制公开性）、单人模式下的功能完善、以及多人化的硬前置。该字段无论是否实施多人化都需补齐，是本节唯一「现在做、不后悔」的动作。若接受 D-21 提前实施，则 0.0.3 的范围需相应更新。其余项应待多人化决策明确后再动。

### 3.3 AI 接入（知识库 + AI）

**状态：⚪ 待评估。** 属大版本，明确不在 0.0.2 ~ 0.0.5 范围，此处仅记录前置条件。

**前置条件（0.0.2 与 0.0.5 即在铺路）：**

- 内容可被检索（FR-002-1 提供雏形）；
- 知识有稳定的引用方式（FR-005-1 / FR-005-2 提供互链基础）；
- `content` 为纯 Markdown，可直接按段落切块（约束见 README 的「跨版本约束与原则」）。

**届时新增的工程量**（仅作预期管理）：内容切片与向量化会引入新的存储表与检索通道，属大版本；届时 AI 的能力边界取决于前两条的完成质量，而不是模型选型。
