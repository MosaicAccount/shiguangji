# 0.0.3 —— 计划

> **版本状态**：✅ 已确定
> **表结构变更**：无（复用既有 `sgj_item.start_date`，状态为自由文本列）
> **设计方案**：尚未产出（开工前需先评审）
> **决策**：D-5 ~ D-10 未拍板，见 [pending.md](pending.md)

## 1. 最终目标

**核心闭环 `想 → 做 → 记` 补上中间两节台阶：产品从「记录发生过的事」扩展到「记录正在发生和打算发生的事」，四个模块共享同一套状态模型。**

现状只有「心愿」与「完成」两端，中间缺的不是一级而是两级：

| 阶段 | 状态表示 | 含义 | 现状 |
| --- | --- | --- | --- |
| 心愿 | `WANT`，无日期 | 「我想看这个」 | 已有 |
| **计划** | `WANT` + `start_date` | 「我打算这周看这个」 | **字段已存在，前台未使用** |
| **执行** | `DOING` | 「我正在看」 | **状态缺失** |
| 完成 | `DONE` | 「看完了」 | 已有 |

从「心愿」到「计划」缺的是**时间**，从「计划」到「完成」缺的是**执行态**。

**注意**：「计划」不是新增状态值，而是「`WANT` + 有日期」的一个视图。因此本期只需新增一个状态值（`DOING`）并复用既有 `start_date`，无需为「排期」引入新枚举。

现有心愿单（首页侧栏 `WISH LIST`）**不是计划，而是计划的素材**：它展示的字段为图标 + 标题 + 状态文案，不含任何日期；`SgjDashboardMapper.selectTodoItems` 按 `create_time desc` 排序，即「最新添加者在前」，既非计划时间也非优先级。**无时间、无次序的清单只增不减，无法回答「下一步做哪个」**，这正是本期要解决的问题。

### 「计划」在两类模块上形状不同

不能用同一个模型硬套：

| 模块 | 「计划」是什么 | 形态 | 实现 |
| --- | --- | --- | --- |
| 电影 / 书籍 | **时间**——「打算哪天看」 | 一个日期 | 复用既有 `start_date` |
| 足迹 | **内容**——「去了要干嘛」 | 一份清单 | 需子项结构，见 [pending.md](pending.md) 的行程清单 |

- **电影**：「想看」加上日期即计划，不存在「变成计划」这个动作，`WANT → DONE` 两步已足够；
- **足迹**：计划的内容侧（清单）不在本版范围。**本版对足迹只补 `start_date` 与 `DOING`，不引入清单。**

### `DOING` 的价值取决于活动是否跨时间

四个模块并不均等：

| 模块 | 典型时长 | `DOING` 的价值 | 可派生的进度 |
| --- | --- | --- | --- |
| 电影 | 约 2 小时 | 低，保留但不强推 | — |
| 电视剧 | 数周 | 高 | 由 `episode_count` 派生「看到第几集」 |
| 书籍 | 数天至数周 | 高 | 由 `pages` 派生阅读进度 |
| 足迹 | 数天 | 中 | 由清单表达更自然 |

**结论**：四个模块共用状态机，但**不要求每个模块都强推三态**；`DOING` 是可用而非必用。

## 2. 范围

`sgj_item` 状态模型扩展、状态字典、前台四个模块的状态流转与筛选、新增计划视图 `/plan`、前台导航调整。涉及影视 / 书籍 / 足迹三个模块，笔记模块不受影响。

**本版只做「计划 = 时间」这一半**；足迹的「计划 = 内容」（行程清单）形状不同且需新增表，不在本版范围。

## 4. 非目标

- 不做集数 / 页数进度（`sgj_item_tv.episode_count`、`sgj_item_book.pages` 目前只存不显，「看到第几集」「读到第几页」需新增字段，留待后续版本；见 D-10）；
- 不做提醒与通知（例如「计划日期临近」）；
- **不做行程容器**（把「某个假期去的 5 个地点」组织成一次行程）。注意它与「行程清单」是两件事：清单是**单个目的地条目内部**的待办子项，容器是**多个条目之间**的归组。前者见 [pending.md](pending.md)，后者暂用现有标签体系凑合（见 D-27），等真实痛点出现再评估。

## 5. 验收标准

- [ ] 三个模块均可在「想看 / 在看 / 看过」（对应书籍、地点）之间流转，流转后列表筛选与详情状态一致；
- [ ] 首页时间线仅含 `DONE`，心愿单仅含 `WANT`，进行中条目不再被错误计入任一侧（见 §7）；
- [ ] `/plan` 页正确汇总 `WANT + DOING`，有日期的按日期排序，无日期的置后，逾期与本周项有视觉区分；
- [ ] 首页 hero 区统计数字在存在进行中条目时仍然自洽，不出现「总数 ≠ 各状态之和」；
- [ ] 首页「完成 →」与各模块「标记看过 / 读过 / 去过」的 `finish_date` 语义一致，补记场景下日期可指定或事后可修正（FR-003-7）；
- [ ] 回归：现有三个模块的「想看 / 看过」筛选、标记与取消标记、首页时间线分页、心愿单「完成 →」快捷操作均无回归。

## 6. 数据与兼容性

- **字典变更**：三套状态字典各新增一条 `DOING`，属新增值，存量数据不受影响；
- **无表结构变更**：`start_date` 是既有字段，本期只是让前台用起来；
- `status` 为自由文本列，无数据库层约束，新增枚举值不需要 DDL。

## 7. 风险提示（本期最大回归风险，已核实）

以下三处对状态做了**写死的二值假设**，新增 `DOING` 后必然出错，必须在本期一并修改：

| 位置 | 现状 | 新增 DOING 后的后果 |
| --- | --- | --- |
| `SgjDashboardMapper.selectTodoItems` | `and status = 'WANT'` | 进行中条目不在心愿单中（预期行为，但需确认是否要纳入） |
| `SgjDashboardMapper.selectTimeline` / `countTimeline` | `and status = 'DONE'` | 进行中条目不在时间线中，且 `timelineTotal` 与列表长度可能不一致 |
| `AppHomeServiceImpl.buildSummary` | `if ("DONE".equals(status)) {...} else { wish... }` | **进行中条目会被静默计入「心愿」统计**，`wishTotal` 与心愿单实际条数不符 |

第三处是 `else` 兜底分支吞掉了所有非 `DONE` 状态，属于隐蔽错误：不报错，只是数字不对。本期必须把该分支改为显式三态判断。
